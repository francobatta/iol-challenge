<plan mode>
We have implemented a first version of the notification API. For now, the API accepts new apps,
  users, user lists, and endpoints.

  Now we need to design the actual notification endpoint and handling of said notifications. For
  that, the naive approach is to have either a) a job reading a global SQL table of jobs/messages
  pending, or b) worker queues per notification strategy (sms, email, etc.)

  While (a) is correct and viable for a small-ish service, multiple tenants scanning the table and
  updating may result in high contention; (b) is naive in regards to starvation, potential rate
  limiting against providers, timeouts, error handling and at-least-once semantics. If we are going to use queues,
  we need them to be effectively distributed to avoid bottlenecks and starvation and bad error handling.

  We must propose an implementation that addresses the limitations in (a) and (b), have it be
  easily scalable (simple, i'm thinking KEDA or similar) while avoiding problems of millions of
  pending messages, and have a more robust error handling while having the possibility of tracing,
  observability and event status tracking in a simple way.

  My idea is to use rabbitMQ with disk persistence (to avoid lost messages, support deadlettering and support ACKs), one queue per (app_id, provider) tuple.
  To avoid starvation, using one queue per tuple is OK. To avoid intra-queue starvation and support of high priority notifications, use a priority header based on the notification job metadata (provided by the app client).

  To scale up message sending, scale up workers consuming a certain queue based on querying its length (the query is received by KEDA). To efficiently scale up the workers, know that we will deliver 16 million notifications PER TENANT PER DAY with reasonable time frames (latency <1s for each notification processing) and reasonable cloud costs and worker count.
  When a notification is sent, the worker ACKs if sent correctly, and thus the message is erased from rabbitMQ's disk. There is a cron job or other similar mature mechanism at api updating the job metadata for each job, updating the rate limits and current usage (avoid overengineering this part - simple and performant first).

  Let's plan this task, ping-pong alternatives, discuss potential pitfalls or alternatives, discuss a new service (or not) for this
  requirement, and interview in the process.
For the worker, we will have it fully implemented, minimal compose implementation working. Providers: mimicry of
     twilio, mailchimp, ios and android for example. Have the provider processing take from 1ms to 1s at
     random to have some rough idea of the real provider latency. KEDA manifests (Deployment,
     ScaledObjects, Service, etc. if needed). Scaling math is documented

     Use a circuit breaker to avoid overwhelming the providers with 429s and exponential backoff for messages
