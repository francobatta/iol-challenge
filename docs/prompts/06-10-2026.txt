Let's simplify this flow. Instead of creating the message and having a 'dispatcher' abstraction,
  have api:
  1. Create another row in a pg jobs table correctly refering to the notification event, with the user cursor
  2. Create the messages using a very efficient users table navigation. Instead of making 2000 queries if we want to send
  a notification to 2000 users, we should use one query and retrieve the whole dataset using indexes like BRIN or
  something ordered in favor of index searches, and having the users conveniently arranged as to have said query be fast
  and avoid N+1
  3. Have api have dispatcher goroutines that periodically fan-out and create the messages sent to the corresponding
  rabbit queues.

  This makes the design simpler, makes use of goroutines and pg rows (with a cron or similar abstraction, native to
  goroutines) instead of a publish of an event to rabbit, and keeps components smaller.

  For this task avoid large plans, and make sure the resulting abstractions are simpler and more maintainable, avoiding
  unnecessary round trips, avoiding outboxes (unless it's necessary - like the job cursor row) and avoiding N+1.
