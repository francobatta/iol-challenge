# Audience API design

Date: 2026-10-05

## Goal

A Go REST API over Postgres that is the contract layer of a notifications service. This first
part manages *who can be notified*: apps (the clients), their users, each user's endpoints
(devices and addresses), and app-owned lists of users. Registering and sending notifications
is out of scope.

## Decisions taken in the interview

| Topic | Decision |
|---|---|
| App entity | Stored in an `apps` table; the API only creates apps |
| App creation | `POST /v1/apps` guarded by a static admin key (`X-Admin-Key`) |
| App auth | HS256 JWT, `sub = app_id`, no expiry, verified by signature only |
| IDs | `user_id` supplied by the app; `app_id`, `endpoint_id`, `list_id` are server UUIDs |
| User create | `PUT /users/{user_id}`, idempotent |
| Channel / provider | `channel` is one of `email`, `sms`, `push`; `provider` is free-form |
| Uniqueness | `(app_id, user_id, channel, address)` on endpoints; `(app_id, name)` on lists |
| Deletes | Hard deletes that cascade |
| Edits | `PATCH` on endpoints and lists |
| Membership | One at a time, plus a bulk add |
| Pagination | Keyset cursor: `?limit=&after=` |
| Stack | `net/http`, pgx v5, sqlc, `golang-jwt/jwt/v5` |
| Tests | In-memory fake store for HTTP and service tests; real Postgres for the repo |

## Packages

The system lives in `notification-system/`, which holds `compose.yaml`. The API is the Go
module in `notification-system/api/`, with its own `Dockerfile`; the paths below are relative
to it.

| Package | Role |
|---|---|
| `cmd/server` | Reads config from the environment, wires dependencies, runs the server |
| `internal/api` | Routing, authentication, JSON, mapping errors to status codes |
| `internal/audience` | Domain types, `Service` (validation and rules), and the `Store` interface |
| `internal/audience/audiencetest` | In-memory `Store` for tests |
| `internal/postgres` | `Store` implementation over sqlc-generated queries |
| `internal/postgres/queries` | Code generated by sqlc from `db/` |
| `internal/token` | Issues and verifies app tokens |

`audience.Store` is the only interface. It is defined by its consumer and has two
implementations (Postgres and the fake). Handlers hold a concrete `*audience.Service`.

## Data model

Defined in `db/schema.sql`, which both sqlc and the Docker Postgres read. There is no
migration tool yet.

```
apps         (app_id uuid PK, name, created_at)
users        (app_id, user_id text, created_at)                      PK (app_id, user_id)
endpoints    (app_id, endpoint_id uuid, user_id, address, channel, provider)
                                                                     PK (app_id, endpoint_id)
lists        (app_id, list_id uuid, name, description, created_at)   PK (app_id, list_id)
list_members (app_id, list_id, user_id, added_at)                    PK (app_id, list_id, user_id)
```

- Server IDs default to `uuidv7()` (Postgres 18), so primary-key order is creation order.
- Foreign keys are composite and `ON DELETE CASCADE`: endpoints -> users, list_members ->
  users and lists, users and lists -> apps.

## HTTP API

All routes are under `/v1` and speak JSON. Every route except `POST /v1/apps` requires
`Authorization: Bearer <token>`; the `app_id` always comes from the token.

| Method and path | Success | Notes |
|---|---|---|
| `POST /apps` | 201 app + `token` | `X-Admin-Key` required; body `{name}` |
| `PUT /users/{user_id}` | 201 created, 200 existed | |
| `GET /users/{user_id}` | 200 | |
| `GET /users` | 200 page | ordered by `user_id` |
| `DELETE /users/{user_id}` | 204 | cascades |
| `POST /users/{user_id}/endpoints` | 201 | body `{address, channel, provider}` |
| `GET /users/{user_id}/endpoints` | 200 page | ordered by `endpoint_id` |
| `GET /endpoints/{endpoint_id}` | 200 | |
| `PATCH /endpoints/{endpoint_id}` | 200 | any of `address`, `channel`, `provider` |
| `DELETE /endpoints/{endpoint_id}` | 204 | |
| `POST /lists` | 201 | body `{name, description}` |
| `GET /lists` | 200 page | ordered by `list_id` |
| `GET /lists/{list_id}` | 200 | |
| `PATCH /lists/{list_id}` | 200 | any of `name`, `description` |
| `DELETE /lists/{list_id}` | 204 | cascades |
| `PUT /lists/{list_id}/members/{user_id}` | 204 | idempotent |
| `DELETE /lists/{list_id}/members/{user_id}` | 204 | idempotent; 204 even if not a member |
| `GET /lists/{list_id}/members` | 200 page | ordered by `user_id` |
| `POST /lists/{list_id}/members` | 204 | body `{user_ids}`, 1 to 1000 |

**Pages.** `?limit=` (default 50, max 200) and `?after=<last id of the previous page>`.
The body is `{"items": [...], "next_after": "..."}`; `next_after` is omitted on the last page.

**Malformed IDs.** An `endpoint_id`, `list_id` or `after` cursor that is not a UUID is
treated as an ID that does not exist: 404 for a single resource, an empty page for a cursor.

**Bulk add** is all-or-nothing: if any `user_id` is unknown nothing is added and the 404
message names the unknown IDs. Users already in the list are skipped.

**Errors.** `{"error": {"code": "...", "message": "..."}}`.

| Status | Code | When |
|---|---|---|
| 400 | `invalid_request` | malformed JSON, unknown JSON field, failed validation, bad `limit` |
| 401 | `unauthorized` | missing or invalid token or admin key |
| 404 | `not_found` | the user, endpoint or list does not exist in this app |
| 409 | `conflict` | duplicate list name or duplicate endpoint |
| 500 | `internal` | anything else; the cause is logged, not returned |

**Validation.** `user_id` is 1 to 255 characters. `name`, `address` and `provider` are
non-empty. `channel` is `email`, `sms` or `push`.

## Errors in Go

`audience` exports three sentinels, `ErrInvalid`, `ErrNotFound` and `ErrConflict`. Stores and
the service wrap them with a short detail; `api` maps them with `errors.Is`. The Postgres
store translates `pgx.ErrNoRows` and foreign-key violations to `ErrNotFound`, and unique
violations to `ErrConflict`.

## Configuration

Environment variables: `DATABASE_URL`, `JWT_SECRET`, `ADMIN_KEY` (all required) and `ADDR`
(default `:8080`). The server exits at start-up with a message naming a missing variable.

## Testing

- `api`: table-driven tests through `httptest` against the real service over the fake store.
- `audience`: validation rules of the service.
- `token`: round trip and rejection of tampered or foreign tokens.
- `postgres`: against a real database; skipped when `DATABASE_URL` is unset.
- `notification-system/compose.yaml` starts Postgres 18 with the schema loaded, and the service.
